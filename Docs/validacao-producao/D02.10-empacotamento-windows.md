# D02.10 — Empacotamento Windows

## Escopo e referência
Implementação remota, sem execução no SED-TI-D05. Nenhum instalador, serviço, firewall, ACL,
registro, banco, migration ou dado de produção é alterado por esta etapa.
Base inspecionada: 64dab3fd7e69e408768cfca37420d525a38cb699; main inclui a D02.9 e Flyway V1–V25.
Não alterar 250 monitores, intervalo de 60s, 30 dias UTC completos ou pressupor expansão do SSD.

## Auditoria dos artefatos
CI Backend e CI Frontend publicam respectivamente:
backend-<sha>-<run-id>-<attempt> e frontend-<sha>-<run-id>-<attempt>.
Backend: JAR infra-monitor-backend-<sha>.jar, build-manifest.json (component,commit,run_id,sha256),
SHA256SUMS. Frontend: wwwroot, build-manifest.json (configuration=production), SHA256SUMS.
Angular usa API relativa /api/v1 e saída dist/infra-monitor-frontend/browser.
application-prod.yml usa INFO e health sem detalhes. GET /actuator/health é público no backend,
mas este modelo IIS bloqueia /actuator: a inspeção é somente via loopback no host.
Variáveis de datasource têm defaults de desenvolvimento: provisionar valores de produção,
nunca depender dessas credenciais padrão. JWT_SECRET é obrigatório.
Motor, Telegram, dispatcher, manutenção e retenção ficam desligados sem habilitação explícita.
Retenção conserva enabled=false/dry-run=true/deletion-approved=false.
JNA usa IPHLPAPI/IcmpSendEcho no Windows; permissões, arquitetura x64, DLL nativa, temp Java e
parada graciosa precisam de homologação sob a identidade real do serviço, sem presumir administrador.

## Arquitetura e confiança
Workflow CI Windows Packaging preserva os workflows existentes.
Em PR, empacota a aplicação do commit base main já aprovado; não confundir essa versão com
o commit da lógica de empacotamento do PR. Push main usa o commit do push; manual exige SHA explícito.
O resolver aceita somente runs push/main bem-sucedidos dos caminhos exatos dos dois workflows,
mesmo repositório e commit, nome de artefato incluindo run/attempt e sem expiração.
Nenhum artefato de PR é promovido automaticamente. Até 10 minutos de espera por workflow;
ausência, falha ou artefatos expirados bloqueiam, sem reconstrução ou mistura silenciosa.

A montagem valida hash de todos os payloads, manifestos, versão, index.html, JAR Spring Boot
e classe de proteção de histórico V25. Rejeita extras, paths absolutos/.., links, nomes divergentes,
case collisions e padrões conhecidos de credenciais/chaves. O scanner não é prova de ausência
de todo segredo: revisar recursos e comparar a origem/digest publicado pelo GitHub.
Checksums sem origem confiável não autenticam um pacote contra adulteração deliberada.
Tokens de runtime do Actions não entram no conteúdo. O job assemble recebe somente actions:read
e contents:read; não há secrets, pull_request_target, runner próprio ou deploy.

Pacote:
- releases/r-<sha completo>/backend/app.jar
- releases/r-<sha completo>/frontend/ (Angular e web.config)
- package-manifest.json, SHA256SUMS
- ReleaseTools.psm1, Invoke-WindowsRelease.ps1, modelos XML/IIS
Manifesto inclui os manifests de origem e IDs de run/artefato. Compatibilidade de schema
não é declarada comprovada automaticamente. WinSW, JDK, PostgreSQL e instaladores não são incluídos.
Retenção do artefato de homologação: 7 dias. Fixtures sintéticas nunca são publicadas como aplicação.

## Diretórios futuros (raiz absoluta escolhida pelo operador)
<root>/releases/<versao>/{backend,frontend}
<root>/current/{backend,frontend} -- junctions independentes, com ponteiros .previous
<root>/config/{secrets,service,compatibility}
<root>/config/deployment-state.json
<root>/logs/{backend,service} e deployment.ndjson
<root>/staging/<versao>

Current não é cópia do release. O serviço e IIS usam esses caminhos estáveis.
IIS físico: <root>/current/frontend; Java: <root>/current/backend/app.jar.
State inicial deve ser provisionado pelo operador, por exemplo backend=none/frontend=none;
bootstrap de dependências, serviço, site e ACL é procedimento separado, não feito pelos scripts.
Staging mantém uma cópia candidata; promoção move os binários no mesmo volume.
No máximo duas releases persistentes. Com duas existentes, Stage bloqueia até revisão e remoção
manual explicitamente autorizada da anterior dispensável. Nenhuma limpeza automática libera espaço.
Restos de staging, ponteiros .previous e evidências exigem revisão humana; não remover targets por
uma junction. Uma falha preserva evidências e mantém o site parado para recuperação específica.

## Pré-requisitos e WinSW
Windows 11 Pro x64, PowerShell 7.2+ para operação, Java 21 x64, PostgreSQL 16 local,
.NET Framework 4.6.1+ para WinSW 2.12.0 x64, IIS Static Content, URL Rewrite 2 e ARR.
WinSW é obtido separadamente de sua release oficial, versão e SHA-256 aprovados pelo operador.
Não há download automático. Test-Prerequisites verifica Java pelo arquivo release, postgres.exe,
hash WinSW, módulos IIS, .NET e ACL dos segredos; não cria ou reconfigura nenhum deles.
O modelo winsw.xml.template NÃO é configuração final: substituir @@JAVA_EXE@@, @@ROOT@@ e
@@ROOT_URI@@ com paths absolutos revisados (XML escaping correto; ROOT_URI usa barras /).
Provisionar final XML protegido fora de releases, ao lado do wrapper, com o mesmo basename.
Modelo: Java direto, perfil prod, endereço 127.0.0.1:8080, configtree externo obrigatório,
Flyway desabilitado, shutdown graceful 30s, WinSW stoptimeout 45s, reinícios limitados,
conta virtual NT SERVICE/InfraMonitorBackend e start Manual.
Não usar LocalSystem como fallback. Validar suporte dessa conta virtual na distribuição WinSW
selecionada, direito de logon como serviço e acesso mínimo na homologação.
Não instalar serviço nem executar XML pelo CI. Ctrl+C/árvore de processos e parada real precisam
de ensaio WinSW: não considerar a sintaxe XML prova de shutdown gracioso no servidor.

## Segredos e ACL
Operador provisiona arquivos configtree (sem conteúdo real versionado):
config/secrets/DB_NAME, DB_USERNAME, DB_PASSWORD, JWT_SECRET.
Adicionar TELEGRAM_BOT_TOKEN/TELEGRAM_CHAT_ID somente em ativação autorizada.
Configurar CORS_ALLOWED_ORIGINS para o HTTPS interno aprovado.
Cada arquivo deve ser não vazio, sem newline desnecessário; JWT com pelo menos 32 bytes.
Desabilitar herança de ACL: Administrators/SYSTEM e SID exato da conta de serviço,
serviço somente leitura. IIS/AppPool não recebe acesso a config, segredos ou backend.
ACL de raiz, releases, state, prova de compatibilidade e XML final é provisionada separadamente;
script não concede privilégios nem escreve segredos. Não colocar valores em linha de comando,
transcripts, manifests, logs ou XML. Não copiar segredos para staging/releases.
Configtree é importado explicitamente pelo comando Java; Spring não lê .env automaticamente.
DB_HOST/DB_PORT no modelo apontam para 127.0.0.1:5432. Nenhuma migration roda na partida:
aplicação V1–V25 é processo distinto, com autorização e evidência, antes da ativação.

## IIS e HTTPS
Instalar e configurar módulos/ARR proxy somente no procedimento autorizado posterior.
Binding de hostname aprovado obrigatório: não aceitar host header arbitrário via wildcard.
Associar certificado interno válido e sua cadeia confiável. O modelo redireciona HTTP para HTTPS,
preserva /api/v1 e query string, encaminha somente para 127.0.0.1:8080.
Bloqueia /actuator, configurações, logs e diretórios privados. Nenhum endpoint health exposto
pelo proxy; operadores usam loopback. SPA somente GET/HEAD e rotas sem extensão inexistentes;
assets ausentes permanecem 404, APIs desconhecidas não recebem index.html.
HTML e assets sem fingerprint: no-store; JS/CSS com hash Angular: um ano/immutable.
Configurar MIME para .mjs/.woff2 se ausente, após verificar a configuração herdada do site.
Rotação IIS é configuração de site/server, não web.config: arquivo diário, orçamento total
128 MiB/até 7 dias (tamanho pode encurtar retenção), monitoramento e procedimento humano de limpeza.
WinSW roll-by-size: 2 MiB, 4 arquivos por stream; monitorar também o log próprio do wrapper.
Spring rolling: 20 MB, total 192 MB, até 7 dias. Esses limites não controlam dumps/event logs.
Windows 11 Pro/IIS permite 10 requisições em execução simultânea; excesso enfileira.
Ensaiar dashboards, CSV/PDF, clientes lentos, timeouts ARR e cache sob concorrência. 250 monitores
não equivalem a 250 clientes HTTP. Não há garantia de desempenho por usar runner Windows Server.

## Scripts e aprovação
Invoke-WindowsRelease.ps1 usa Operation explícita:
Inspect (padrão), Prerequisites, Verify, Space, Stage, Health, Switch e Rollback.
Root e demais caminhos são absolutos locais; paths de volume, traversal e reparse inesperado
são rejeitados. Comandos de leitura não criam arquivos; Health faz somente GET loopback.
Stage/Switch/Rollback sem Apply retornam um plano, sem escrever.
Mutação exige -Apply, -ApprovalId e ShouldProcess; -WhatIf bloqueia os efeitos.
Não executar estes scripts no SED-TI-D05 nesta etapa.
Não há Install-Service, instalação IIS, firewall, ACL ou banco no pacote.

Exemplo apenas de inspeção futura (não executado):
pwsh -File <caminho-absoluto>/Invoke-WindowsRelease.ps1 -Root <raiz-absoluta> -PackagePath <pacote-absoluto>
Os valores entre sinais <> são placeholders, não comandos prontos.

## Espaço e atualização
Bloquear se livre projetado após cópia + pico ficar abaixo de 22 GiB; 20 GiB nunca é orçamento
de staging. Stage soma tamanho integral do pacote e 1 MiB de metadados. Pico inicial proposto:
3 GiB (crescimento Windows e operação extraordinária), aumentar com evidência; nunca reduzir
para contornar capacidade. Na troca, staging já está contabilizado no livre atual.
O pacote e a cópia descompactada externa também ocupam disco e devem ser medidos antes de copiar
para o servidor. Não duplicar instaladores. Sem expansão do SSD como premissa.
A liberação de capacidade continua dependente de benchmark e orçamento D02.7.

1. Obter pacote e origem confiável, verificar hashes; provisionar dependências/config separadamente.
2. Prerequisites, Verify e Space; revisar dry-run e espaço pós-operação.
3. Stage com aprovação explícita; verificar novamente o conteúdo.
4. Preparar prova externa de compatibilidade e state protegido.
5. Switch com Root, Version, Component, CompatibilityProof, SchemaVersion=25, ServiceName,
   SiteName, JavaHome, ServiceSid, WinSWExecutable, WinSWSha256, PostgreSQLHome e aprovação.
6. Parar site e backend quando aplicável, trocar junctions e iniciar backend; testar health local.
7. Persistir state e reabrir site só com health UP. Testar HTTPS/SPA/API manualmente em homologação.
8. Falha mantém site parado, não faz downgrade de schema nem rollback automático.

## Rollback e compatibilidade
Frontend e backend podem ser selecionados separadamente por Component; Both troca ambos.
A prova deve identificar pares exatos antes/depois, inclusive quando somente um componente muda:
approved=true, schemaVersion=25,
current: {backend: r-<sha>, frontend: r-<sha>},
target: {backend: r-<sha>, frontend: r-<sha>}.
A aprovação é uma evidência humana externa, protegida por ACL; não é gerada como prova pelo CI.
Mesmo frontend isolado exige combinação API comprovada. Backend alvo deve conter proteção histórica.
Não presumir compatibilidade de JAR anterior ao V25, nem restaurar histórico apagado ao reverter.
Sem prova ou target local íntegro, bloquear. Nunca executar undo/clean/migrate no rollback.
Ponteiros .previous não são prova de compatibilidade; exigem conferência com state.
Uma falha entre troca de ponteiros e state é recuperação assistida com site parado; não repetir
comandos cegamente. Não há promessa de troca sem interrupção.

## Testes e critérios de aceitação
Python unittest testa integridade, commits, pacote incompleto, manifests, nomes/paths, credenciais
conhecidas e montagem com fixtures. Runner Windows verifica sintaxe PS/XML, espaço insuficiente,
health simulado, rollback incompatível e padrão sem efeitos. Job final verifica hashes do pacote
real em Windows. Nenhum JAR, serviço, IIS, PostgreSQL ou retenção é executado pelo packaging.
Aceitar somente os três jobs aprovados e CI Backend/Frontend aprovados no commit do PR.
A versão da aplicação do pacote em PR é a main base aprovada, explicitada no manifesto.
Pendente: homologação real IIS/ARR/HTTPS/WinSW/JNA, concorrência e SSD; códigos e modelos não
constituem instalação homologada. Nenhum merge/deploy ou D02.11 automático.
