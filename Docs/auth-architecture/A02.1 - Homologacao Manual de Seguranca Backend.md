A02.1 — Homologação Manual de Segurança Backend — Infra Monitor

1. Objetivo

Executar uma homologação manual e controlada da segurança implementada na A02, validando o comportamento real do backend com PostgreSQL de teste e requisições HTTP reais.

Esta fase não deve criar novas funcionalidades.

O objetivo é comprovar em ambiente executável:

login;

JWT;

/auth/me;

401;

403;

ADMIN;

OPERADOR;

VISUALIZADOR;

usuário inativo;

JWT já emitido após desativação;

proteção do último ADMIN;

reset administrativo de senha;

troca da própria senha;

trocaSenhaObrigatoria;

ausência de secrets/logs indevidos.

2. Pré-condições

A A02 já implementou:

usuarios
JWT bearer stateless
BCrypt
ADMIN / OPERADOR / VISUALIZADOR
bootstrap ADMIN
/auth/login
/auth/me
/usuarios/**
RBAC
401/403 padronizados

Antes de testar:

revisar git status;

iniciar PostgreSQL isolado de teste;

iniciar backend atualizado;

habilitar bootstrap ADMIN por environment;

usar JWT secret de teste apenas no processo;

confirmar /actuator/health;

confirmar ausência de frontend nesta validação;

não expor secrets no relatório.

3. Ambiente

Registrar:

Backend URL:
PostgreSQL:
JWT issuer:
Access token TTL:
Bootstrap ADMIN:

Não registrar valores de senha ou JWT secret.

4. Massa de teste

Criar/usar contas isoladas:

ADMIN principal
OPERADOR de teste
VISUALIZADOR de teste
ADMIN secundário, quando necessário

Não reutilizar credenciais reais.

BLOCO A — BOOTSTRAP E LOGIN

5. Passo 1 — Bootstrap ADMIN

Iniciar backend com:

BOOTSTRAP_ADMIN_ENABLED=true

e variáveis necessárias.

Validar:

aplicação inicia;

ADMIN é criado;

senha está hashada;

não existe senha plaintext no banco;

log não mostra senha.

6. Passo 2 — Idempotência do bootstrap

Reiniciar backend com a mesma configuração.

Validar:

não duplica ADMIN;

não altera senha silenciosamente;

não cria segundo registro.

7. Passo 3 — Login ADMIN

Executar:

POST /api/v1/auth/login

com e-mail e senha válidos.

Esperado:

200
accessToken presente
expiresIn ≈ 900
usuario.papel = ADMIN

Não registrar token completo no relatório.

8. Passo 4 — /auth/me

Executar:

GET /api/v1/auth/me
Authorization: Bearer <token>

Esperado:

200
id
nome
email
papel=ADMIN
ativo=true
trocaSenhaObrigatoria

BLOCO B — 401 / 403

9. Passo 5 — API protegida com token

Executar:

GET /api/v1/dashboard/resumo

com JWT ADMIN.

Esperado:

200

10. Passo 6 — API protegida sem token

Mesma chamada sem Authorization.

Esperado:

401
code = UNAUTHORIZED

Confirmar envelope ApiError.

11. Passo 7 — Token inválido

Executar chamada com bearer inválido/malformado.

Esperado:

401
UNAUTHORIZED

Sem stacktrace público.

BLOCO C — OPERADOR

12. Passo 8 — Criar OPERADOR

Como ADMIN:

POST /api/v1/usuarios

Criar OPERADOR com senha temporária válida.

Esperado:

201
papel=OPERADOR
ativo=true
trocaSenhaObrigatoria=true

13. Passo 9 — Login OPERADOR

Executar login do OPERADOR.

Esperado:

200
papel=OPERADOR

14. Passo 10 — OPERADOR pode mutar inventário

Executar uma mutação segura, por exemplo:

POST /api/v1/tipos-equipamento

ou recurso isolado equivalente.

Esperado:

201

Se preferir não poluir dados, criar registro de teste identificável e limpar/desativar depois.

15. Passo 11 — OPERADOR não acessa Usuários

Executar:

GET /api/v1/usuarios

com token OPERADOR.

Esperado:

403
code = FORBIDDEN

16. Passo 12 — OPERADOR pode fechar Incidente

Usar Incidente controlado de teste.

Executar:

PATCH /api/v1/incidentes/{id}/fechar

Esperado:

permitido

Se não houver Incidente de teste disponível, criar cenário controlado de acordo com ferramentas já existentes.

BLOCO D — VISUALIZADOR

17. Passo 13 — Criar VISUALIZADOR

Como ADMIN:

POST /api/v1/usuarios

Esperado:

201
papel=VISUALIZADOR

18. Passo 14 — Login VISUALIZADOR

Esperado:

200

19. Passo 15 — VISUALIZADOR pode ler

Executar:

GET /api/v1/equipamentos

Esperado:

200

20. Passo 16 — VISUALIZADOR não pode mutar

Executar mutação equivalente:

POST /api/v1/equipamentos

ou recurso de teste válido.

Esperado:

403
FORBIDDEN

BLOCO E — USUÁRIO INATIVO

21. Desativar OPERADOR

Como ADMIN:

PATCH /api/v1/usuarios/{id}/desativar

Esperado:

200
ativo=false

22. Login de usuário inativo

Tentar novo login.

Esperado:

401 ou erro de autenticação definido
ACCOUNT_DISABLED

conforme contrato implementado.

23. JWT já emitido

Usar o token do OPERADOR obtido antes da desativação.

Executar uma API protegida.

Esperado:

acesso negado

Não aguardar expiração de 15 minutos.

Este é um critério obrigatório.

BLOCO F — SENHAS

24. Reset administrativo

Como ADMIN:

PUT /api/v1/usuarios/{id}/senha

definir nova senha temporária.

Validar:

senha antiga não autentica
senha nova autentica
trocaSenhaObrigatoria=true

25. Troca da própria senha

Com usuário autenticado:

PUT /api/v1/usuarios/me/senha

enviar:

senhaAtual
novaSenha

Esperado:

sucesso
trocaSenhaObrigatoria=false

Depois validar:

senha antiga falha
senha nova funciona

26. Senha atual incorreta

Tentar troca com senha atual inválida.

Esperado:

erro controlado

Sem revelar hash ou detalhes internos.

BLOCO G — ÚLTIMO ADMIN

27. Auto-desativação

Como ADMIN autenticado, tentar desativar a própria conta.

Esperado:

bloqueado

com erro de negócio adequado.

28. Último ADMIN ativo

Com apenas um ADMIN ativo, tentar:

desativar último ADMIN

e:

rebaixar último ADMIN

Esperado:

bloqueado
BUSINESS_CONFLICT ou código equivalente

29. ADMIN secundário

Criar segundo ADMIN.

Então validar que operações antes proibidas podem ser permitidas quando não deixam o sistema sem ADMIN ativo, conforme regra implementada.

Não deixar ambiente sem ADMIN válido ao final.

BLOCO H — EMAIL CASE-INSENSITIVE

30. Login com casing diferente

Se usuário foi cadastrado como:

Admin@Empresa.com

tentar login com:

admin@empresa.com

Esperado:

sucesso

31. Duplicidade de e-mail

Tentar criar novo usuário com o mesmo e-mail em casing diferente.

Esperado:

conflito/violação controlada

Não permitir duplicata.

BLOCO I — TOKEN

32. Token expirado

Validar com token expirado por teste controlado/configuração curta, se viável.

Esperado:

401 UNAUTHORIZED

33. Assinatura inválida

Usar token assinado com secret diferente.

Esperado:

401

BLOCO J — CORS / AUTH HEADER

34. Preflight

Validar OPTIONS de origem permitida com:

Access-Control-Request-Headers: Authorization

Esperado:

Authorization permitido
credentials=false

BLOCO K — SEGURANÇA DE LOGS E BANCO

35. Banco

Confirmar:

senha_hash ≠ senha plaintext

Não exibir hash completo no relatório.

36. Logs

Pesquisar por:

Authorization:
Bearer
JWT_SECRET
BOOTSTRAP_ADMIN_PASSWORD
senha

Classificar ocorrências.

Resultado esperado:

nenhum secret/token/senha real logado

BLOCO L — REGRESSÃO DA API

37. Dashboard

Com token autenticado:

GET /dashboard/resumo
→ 200

38. Engine interno

Confirmar que Monitoring Engine continua independente da autenticação HTTP.

Não precisa repetir homologação completa H01.

39. Telegram interno

Confirmar que dispatcher não foi afetado pela proteção HTTP.

Não precisa repetir envio real se código não mudou.

40. Correção de bugs

Se algum passo falhar:

reproduzir
→ identificar causa
→ corrigir minimamente
→ adicionar teste de regressão
→ repetir passo

Não ampliar escopo.

41. Testes automatizados após correções

Executar:

.\mvnw.cmd test

Registrar quantidade.

42. Build

Executar:

.\mvnw.cmd clean package

Resultado obrigatório: sucesso.

testes passam;

build passa.
