R03.6 — Fechamento, Regressão Geral e Homologação Final de Relatórios

Objetivo

Encerrar a R03 comprovando que o módulo de Relatórios está funcional, consistente, seguro, responsivo, acessível e sem regressões.

Esta fase não adiciona novas funcionalidades. Alterações são permitidas apenas para corrigir bugs reais encontrados durante a homologação.

Escopo homologado anteriormente

R02 — Backend de Relatórios

R03.1 — Fundação do Frontend

R03.2 — Disponibilidade

R03.3 — Incidentes e Medições

R03.4 — Latência e Notificações

R03.5 — Visão Geral / Dashboard Analítico

Ambiente obrigatório

Antes dos testes integrados, obrigatoriamente:

Verificar processos nas portas 8080 e 4200.

Encerrar instâncias antigas/obsoletas, se necessário.

Subir PostgreSQL 16 isolado e aplicar migrations.

Subir o backend atualizado em http://localhost:8080.

Confirmar GET /actuator/health = HTTP 200.

Subir o frontend atualizado em http://127.0.0.1:4200.

Confirmar frontend = HTTP 200.

Executar homologação com Chrome/Chromium + Playwright.

Não aceitar “backend/frontend indisponível” sem antes tentar preparar/corrigir o ambiente.

Confirmar DTOs tipados, PageResponse<T>, filtros, datas UTC, paginação e sort server-side.

Bearer deve ser enviado exclusivamente pelo interceptor existente. Não adicionar Authorization manual ao service.

Auditoria analítica

É bloqueador encontrar métricas globais calculadas sobre uma página parcial (content).

Confirmar:

KPIs globais usam totalElements filtrado quando aplicável.

Rankings usam page=0, size=N e sort server-side.

P95 vem da API; não é recalculado no Angular.

Duração analítica de Incidente vem de duracaoSegundosNoPeriodo.

SEM_DADOS e SEM_MONITORAMENTO não são tratados como 0%.

null não é transformado artificialmente em zero.

Períodos

Limites máximos:

Disponibilidade: 365 dias

Incidentes: 365 dias

Medições: 31 dias

Latência: 90 dias

Notificações: 365 dias

Visão Geral: 31 dias

Validar ausência, período invertido, inicio = fim, período válido e excesso de limite. Não truncar silenciosamente.

Filtros dependentes

Revalidar Unidade → Equipamento → Monitor.

Trocar Unidade deve limpar seleções incompatíveis de Equipamento/Monitor e atualizar lookups. Trocar Equipamento deve limpar Monitor incompatível e atualizar seu lookup.

Paginação e sort

Paginação deve ser server-side nas seis áreas paginadas.

Sizes: 10, 20, 50 e 100. Medições usam default 50; demais, default 20. Alterar filtro ou size deve voltar para page=0.

Sort deve usar somente as whitelists homologadas. Não inventar campos no frontend. P95 não deve ganhar sort se o contrato não o suporta.

Null safety e estados

Validar com massa real:

CALCULADO

SEM_DADOS

SEM_MONITORAMENTO

enviadoEm null

A UI não pode exibir NaN, undefined, null ou Infinity.

Visão Geral

Revalidar os três KPIs homologados, ranking de Unidades, Top Equipamentos e Latência por Monitor.

Falha de um widget não pode derrubar os demais. Retry parcial deve repetir somente o widget necessário.

RBAC em browser

Executar login/logout pela UI separadamente com:

ADMIN

OPERADOR

VISUALIZADOR

Para cada papel, acessar /relatorios e todas as sete áreas sem /forbidden, com requests válidas retornando 200.

Network, console e requests

No browser confirmar:

Bearer via interceptor, sem expor token.

parâmetros page, size, sort e filtros corretos.

ausência de bloqueio CORS.

uma interação gera apenas as requests necessárias.

sem erros Angular/template/HTTP inesperados.

sem warnings relevantes.

Responsividade

Executar em 320, 375, 390, 412, 768, 1024 e 1440 px.

Não pode existir overflow horizontal da página. Tabelas extensas podem usar scroll interno controlado.

Acessibilidade

Auditar headings, labels, cabeçalhos de tabela, nomes acessíveis, foco visível, navegação por teclado, ARIA quando aplicável e alternativa textual das visualizações. Informação não pode depender exclusivamente de cor.

Segurança e artefatos

Confirmar ausência de JWT em localStorage, sessionStorage, IndexedDB e cookie de autenticação. Não registrar JWT, Authorization ou senhas no console.

Auditar scripts E2E, screenshots, evidence/result.json e demais artefatos. Não deixar segredos, credenciais, dumps, dados sensíveis ou caminhos pessoais (C:\\Users\\..., /Users/...).
