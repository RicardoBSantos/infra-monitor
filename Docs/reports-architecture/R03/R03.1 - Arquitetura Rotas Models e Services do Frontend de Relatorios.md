R03.1 — Arquitetura, Rotas, Models e Services do Frontend de Relatórios — Infra Monitor

Objetivo

Criar a fundação técnica do frontend de Relatórios consumindo exclusivamente o contrato HTTP homologado na R02.

Estado homologado

R02 HOMOLOGADA COM RESSALVAS. Backend de Relatórios pronto para Frontend: SIM.

Endpoints:

GET /api/v1/relatorios/disponibilidade/equipamentos

GET /api/v1/relatorios/disponibilidade/unidades

GET /api/v1/relatorios/incidentes

GET /api/v1/relatorios/medicoes

GET /api/v1/relatorios/latencia

GET /api/v1/relatorios/notificacoes

ADMIN, OPERADOR e VISUALIZADOR possuem READ.

Fontes de verdade

Ler Docs/reports-architecture/reports-architecture.md e Docs/reports-performance.md. Inspecionar app.routes.ts, sidebar, AuthStateService, roleGuard, ApiError, PaginaResposta, services/listagens/filtros/paginação e Design System existentes. Antes de alterar: git status e git diff.

Regra fundamental

O Angular NÃO recalcula disponibilidade, tempos, p95, duração de incidente, estado analítico, qualidade, agregação de Unidade ou status operacional. A API é fonte de verdade.

Implementação

Criar feature /relatorios coerente com a arquitetura existente.

Criar rota /relatorios com lazy loading via loadComponent e proteção autenticada para ADMIN, OPERADOR e VISUALIZADOR.

Adicionar item Relatórios à sidebar para os três papéis.

Criar página-base responsiva que sirva de entrada para Disponibilidade por Equipamento, Disponibilidade por Unidade, Incidentes, Medições, Latência e Notificações. Não implementar ainda as telas analíticas finais.

Criar/reutilizar models tipados fiéis ao backend: DisponibilidadeEquipamentoResponse, DisponibilidadeUnidadeResponse, HistoricoIncidenteResponse, HistoricoMedicaoResponse, LatenciaIcmpResponse e HistoricoNotificacaoResponse. Confirmar campos e nullability no contrato real antes de codificar.

Reutilizar PaginaResposta existente: content, page, size, totalElements, totalPages, first, last.

Reutilizar enums existentes e criar apenas os ausentes, com valores idênticos ao backend.

Criar RelatorioApiService com getDisponibilidadeEquipamentos, getDisponibilidadeUnidades, getIncidentes, getMedicoes, getLatencia e getNotificacoes usando environment.apiUrl.

Não manipular JWT no service. Reutilizar interceptor e tratamento global de 401/403/PASSWORD_CHANGE_REQUIRED.

Criar filtros tipados por endpoint. Não usar Record<string, any> genérico.

Suportar inicio/fim, IDs, enums, page, size e sort conforme contrato. page é zero-based; default geral 20; Medições 50; backend limita size a 100.

Construir HttpParams omitindo null, undefined e string vazia; preservar valores válidos como 0.

Não inventar período default silencioso no service nem converter timezone de forma implícita.

Sort deve aceitar somente campos/opções documentados e direção asc/desc.

Reutilizar ApiError e Design System existentes.

Garantir responsividade em 320/375/390/tablet/desktop e acessibilidade básica.

Filtros mínimos

Disponibilidade Equipamentos: inicio, fim, unidadeId, equipamentoId, monitorId, tipoEquipamentoId, page, size, sort.
Disponibilidade Unidades: período, unidadeId quando suportado, page, size, sort.
Incidentes: inicio, fim, unidadeId, equipamentoId, monitorId, status, page, size, sort.
Medições: inicio, fim, unidadeId, equipamentoId, monitorId, status, page, size, sort.
Latência: inicio, fim, unidadeId, equipamentoId, monitorId, page, size, sort.
Notificações: inicio, fim, incidenteId, status, canal, tipoEvento, page, size, sort.

Testes obrigatórios

rota /relatorios, lazy loading e acesso dos três papéis;

sidebar mostra Relatórios para ADMIN/OPERADOR/VISUALIZADOR;

seis métodos do RelatorioApiService: GET, URL, parâmetros obrigatórios/opcionais e resposta tipada;

serialização de filtros comprova omissão de null/undefined/"";

autenticação continua fora do service;

smoke contra backend autenticado para confirmar JSON real dos seis endpoints.

Executar npm test -- --watch=false e npm run build. Esperado: zero failures e BUILD SUCCESS, sem novo warning relevante de budget.

Fora de escopo

Não implementar gráficos, CSV, PDF, exportação, comparativos avançados, cards/tabelas analíticas finais, novos endpoints, mudança de backend, recálculo de disponibilidade/p95 ou R03.2+.

Critérios de aceite
