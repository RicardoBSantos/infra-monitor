R03.3 --- Histórico de Incidentes e Medições --- Infra Monitor

1. Objetivo

Implementar e homologar no frontend Angular as áreas analíticas de:

Histórico de Incidentes;

Histórico de Medições.

A fase deve consumir exclusivamente os endpoints analíticos já
homologados no backend R02:

GET /api/v1/relatorios/incidentes
GET /api/v1/relatorios/medicoes

A R03.3 deve manter a rota existente:

/relatorios

e integrar Incidentes e Medições à mesma feature de Relatórios criada
nas fases R03.1/R03.2.

2. Pré-condições

Considerar homologados:

R02 — Backend de Relatórios
R03.1 — Fundação dos Relatórios
R03.2 — Disponibilidade por Equipamentos e Unidades

Não alterar contratos backend já homologados para facilitar o frontend.

Não reabrir a implementação de Disponibilidade sem bug real de
regressão.

3. Escopo

Implementar:

Histórico de Incidentes
Histórico de Medições

Incluindo:

filtros;

período obrigatório;

lookups dependentes;

paginação server-side;

sort server-side usando somente whitelist tipada;

loading;

success;

empty;

error;

refresh;

responsividade;

acessibilidade;

testes automatizados;

smoke autenticado;

homologação browser.

4. Fora de escopo

Não implementar nesta fase:

Latência
Notificações
gráficos
CSV
PDF
exportação
novos endpoints backend
novos filtros não suportados pelo backend
alteração de RBAC
mudança na arquitetura de autenticação

Não iniciar automaticamente a próxima fase.

5. Contrato real

Antes de codificar, auditar no frontend e backend:

HistoricoIncidenteResponse
HistoricoMedicaoResponse
RelatorioApiService
RelatorioController
RelatorioService

Usar apenas campos reais.

Não inventar campos.

O contrato de HistoricoMedicaoResponse já foi anteriormente validado
como não possuindo campo mensagem.

6. Histórico de Incidentes --- endpoint

Consumir:

GET /api/v1/relatorios/incidentes

Usar o método tipado existente do:

RelatorioApiService

Não construir URL manual no componente.

7. Histórico de Incidentes --- tabela

A tabela deve representar os campos reais do DTO homologado.

Priorizar, conforme disponibilidade real no DTO:

Unidade
Equipamento
Monitor
Status
Início
Encerramento
Duração no período

Se houver outros campos reais úteis já presentes no DTO, podem ser
exibidos somente se coerentes com o design existente.

Não inventar informação derivada que o backend já fornece.

8. Duração de Incidente

Usar:

duracaoSegundosNoPeriodo

quando este for o campo real homologado.

Formatar duração somente para apresentação.

Não recalcular duração a partir de timestamps no frontend.

O backend continua sendo a fonte da duração analítica recortada pelo
período.

9. Incidente aberto

Se:

encerradoEm = null

a UI deve representar claramente que o incidente permanece aberto.

Não exibir:

Invalid Date
undefined
null

Usar representação textual coerente com o Design System, por exemplo:

—

ou badge/status já existente.

10. Filtros de Incidentes

Implementar somente filtros suportados pelo contrato real.

Auditar antes de codificar.

A matriz esperada inclui, quando suportada pelo backend:

período
unidadeId
equipamentoId
monitorId
tipoEquipamentoId
status

Se algum filtro não existir no backend real, não inventar.

11. Dependências dos filtros de Incidentes

Preservar o comportamento já homologado em Disponibilidade:

Unidade alterada
→ limpa Equipamento
→ limpa Monitor
→ atualiza lookup de Equipamentos

Equipamento alterado
→ limpa Monitor
→ atualiza lookup de Monitores

Não permitir filtros hierarquicamente incompatíveis.

12. Período de Incidentes

O período é obrigatório.

Converter corretamente para o contrato temporal do backend.

Preservar UTC conforme arquitetura já homologada.

Não introduzir conversão que desloque o dia selecionado por timezone.

Respeitar o limite backend homologado:

até 365 dias

O backend continua sendo a autoridade final da validação.

13. Sort de Incidentes

Usar somente campos homologados na whitelist tipada existente.

Não enviar campo arbitrário.

Implementar:

asc
desc

O sort deve ser server-side.

O frontend não deve reordenar apenas os itens da página atual.

14. Paginação de Incidentes

Server-side.

Usar o envelope:

PageResponse<HistoricoIncidenteResponse>

Preservar:

page zero-based
size
totalElements
totalPages
first
last

Sizes disponíveis devem seguir o padrão já adotado pela feature:

10
20
50
100

Default deve respeitar o backend/contrato já existente.

15. Histórico de Medições --- endpoint

Consumir:

GET /api/v1/relatorios/medicoes

via método tipado existente do:

RelatorioApiService

16. Histórico de Medições --- tabela

Exibir apenas campos reais de:

HistoricoMedicaoResponse

Priorizar, conforme DTO real:

Unidade
Equipamento
Monitor
Data/hora da execução
Status
Latência

Não adicionar campo mensagem se ele não existir no DTO.

17. Status da Medição

Representar os enums reais do backend.

Exemplo já homologado:

FALHA

Auditar todos os valores reais do enum antes de criar labels.

Não inferir disponibilidade operacional do Equipamento a partir de uma
Medição isolada.

A fonte do status operacional continua sendo o Dashboard/backend
correspondente.

18. Latência da Medição

Quando houver latência:

exibir em ms

Quando for null:

—

Não transformar null em:

0 ms
NaN
undefined

19. Filtros de Medições

Implementar apenas filtros suportados pelo endpoint real.

A matriz esperada inclui, quando homologada no backend:

período
unidadeId
equipamentoId
monitorId
tipoEquipamentoId
status

Auditar contrato antes da implementação.

20. Dependências dos filtros de Medições

Aplicar a mesma hierarquia:

Unidade
→ Equipamento
→ Monitor

Mudança de Unidade limpa filtros descendentes incompatíveis.

Mudança de Equipamento limpa Monitor incompatível.

21. Período de Medições

Obrigatório.

Respeitar o limite backend homologado:

31 dias

O frontend pode orientar o usuário antes da request, mas o backend
permanece autoridade final.

Validar:

inicio ausente
fim ausente
inicio > fim
inicio = fim
período > 31 dias

Não duplicar regras divergentes das regras do backend.

22. Sort de Medições

Somente whitelist homologada.

Implementar:

asc
desc

Server-side.

Não ordenar localmente a página atual como substituição.

23. Paginação de Medições

Server-side.

Preservar o default específico homologado:

size default = 50

Envelope:

PageResponse<HistoricoMedicaoResponse>

Validar troca de:

10
20
50
100

e reset para:

page=0

quando filtro/sort/size alterar o conjunto.

24. Navegação dentro de Relatórios

Manter a organização visual existente.

Adicionar Incidentes e Medições de forma coerente com as áreas já
existentes.

Não criar nova rota top-level desnecessária.

Esperado:

/relatorios

com navegação interna entre áreas.

A URL pode permanecer /relatorios se esse for o padrão já adotado.

Não redesenhar a feature.

25. Estado dos filtros

Filtros de Incidentes e Medições devem ser independentes.

Trocar de uma área para outra não pode gerar combinação acidental de
filtros incompatíveis.

Preservar estado somente se isso já for comportamento da feature.

Não introduzir persistência em localStorage/sessionStorage.

26. Consulta inicial

Seguir o padrão estabelecido na R03.2.

Se a área carregar automaticamente ao ser aberta, garantir:

uma abertura
→ uma request

Evitar chamadas duplicadas.

27. Refresh

Adicionar/reutilizar ação:

Atualizar

Refresh deve:

preservar filtros
preservar sort
preservar página quando coerente
executar nova request

Não limpar filtros silenciosamente.

28. Loading

Durante consulta:

loading visível

Evitar tabela antiga sendo interpretada como resultado novo se o padrão
atual da feature já limpa/neutraliza o conteúdo durante carregamento.

29. Empty

Quando:

content=[]

mostrar estado vazio claro.

Diferenciar:

sem resultados para os filtros

de:

erro de carregamento

30. Errors

Preservar tratamento existente.

Validar no mínimo:

400 INVALID_REQUEST
404 RESOURCE_NOT_FOUND
500 / erro interno seguro

A UI não deve exibir stack trace.

Deve oferecer recuperação quando apropriado:

Tentar novamente
Atualizar

31. 401 / 403

Não alterar interceptor/auth.

Preservar:

401 → comportamento global existente
403 → sessão preservada
PASSWORD_CHANGE_REQUIRED → comportamento existente

32. RBAC

ADMIN
OPERADOR
VISUALIZADOR

Não criar diferença de conteúdo entre os três papéis nesta fase, salvo
regra backend já existente.
