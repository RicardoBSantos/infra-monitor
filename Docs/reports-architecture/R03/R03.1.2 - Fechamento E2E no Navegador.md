R03.1.2 --- Fechamento E2E no Navegador

Objetivo

Fechar a única ressalva restante da R03.1: produzir evidência E2E no
navegador de que o frontend Angular autenticado acessa /relatorios,
utiliza o interceptor existente para enviar o Bearer token, consome os
seis endpoints de relatórios sem erro de CORS e não produz erros
inesperados no console.

Esta fase é exclusivamente de homologação. Não iniciar R03.2 e não
alterar código salvo se um bug real for reproduzido.

Estado de entrada

A R03.1.1 já comprovou:

frontend respondendo em http://127.0.0.1:4200;

backend respondendo em http://localhost:8080;

PostgreSQL isolado;

login ADMIN, OPERADOR e VISUALIZADOR;

seis endpoints de relatórios retornando 200;

DTOs compatíveis;

paginação compatível;

Medições com size=50 por default;

filtros e sort validados;

CORS/preflight aprovado com Authorization;

87 testes frontend, zero falhas;

build frontend aprovado;

nenhum bug de contrato;

nenhum arquivo alterado.

Não repetir validações profundas de SQL, DTO, paginação, filtros ou
performance sem necessidade.

Escopo obrigatório

1. Preparação

Antes de qualquer alteração:

git status
git diff

Subir o backend e frontend homologados.

Confirmar:

GET http://localhost:8080/actuator/health -> 200
GET http://127.0.0.1:4200 -> 200

Usar PostgreSQL isolado de teste quando necessário.

Não expor secrets, senhas, JWT completo, Authorization completo ou
JWT_SECRET no relatório, screenshots ou logs.

2. Browser real

A validação deve acontecer em navegador real ou automação de navegador
capaz de observar:

navegação;

requests de rede;

status HTTP;

console;

reload/F5.

Não considerar chamadas HTTP externas ao Angular como substitutas desta
evidência.

3. ADMIN

Fazer login pela UI como ADMIN.

Confirmar:

login concluído;

rota autenticada carregada;

item Relatórios visível;

navegação pela UI até /relatorios;

/relatorios renderizado sem erro;

nenhuma exceção inesperada no console.

4. Bearer pelo interceptor

A partir de uma chamada originada pelo Angular, observar no Network que
o request de relatório contém o header:

Authorization: Bearer <redacted>

No relatório registrar apenas:

Authorization Bearer presente: SIM/NÃO

Nunca copiar o token.

Confirmar também por inspeção do código que RelatorioApiService não
adiciona Authorization manualmente.

5. Seis endpoints originados pelo Angular

Gerar/observar chamadas originadas pela aplicação Angular para:

/api/v1/relatorios/disponibilidade/equipamentos
/api/v1/relatorios/disponibilidade/unidades
/api/v1/relatorios/incidentes
/api/v1/relatorios/medicoes
/api/v1/relatorios/latencia
/api/v1/relatorios/notificacoes

Se a landing page atual não dispara automaticamente esses seis requests,
é permitido usar o fluxo existente da aplicação/test harness de browser
sem criar feature de produção. Não adicionar chamadas artificiais
permanentes à landing page apenas para homologação.

Para cada request observar:

origem no frontend Angular;

Bearer presente;

status esperado 200;

ausência de bloqueio CORS;

resposta JSON válida.

6. OPERADOR

Fazer logout/login pela UI como OPERADOR.

Confirmar:

login funciona;

Relatórios visível;

/relatorios acessível;

rota não redireciona para /forbidden;

chamada autenticada de relatório retorna 200;

console sem erro inesperado.

Não é necessário repetir toda a matriz dos seis endpoints se a R03.1.1
já a comprovou via HTTP para esse papel. O objetivo aqui é comprovar o
fluxo Angular/browser.

7. VISUALIZADOR

Repetir a evidência mínima de browser:

login pela UI;

Relatórios visível;

/relatorios acessível;

chamada autenticada retorna 200;

console sem erro inesperado.

8. CORS

No browser, confirmar que não aparecem erros como:

blocked by CORS policy
preflight failed
Request header field authorization is not allowed

Registrar somente a conclusão e, se houver falha, a mensagem necessária
para diagnosticar sem expor credenciais.

9. Console

Limpar o console antes do cenário principal.

Executar navegação e requests.

Classificar:

erros da aplicação;

erros HTTP inesperados;

erros Angular;

erros de template;

erros CORS;

warnings relevantes.

Ruído comprovadamente externo à aplicação deve ser identificado
separadamente e não tratado como bug do Infra Monitor.

Critério esperado:

Erros inesperados da aplicação: NÃO

10. F5 / reload

Com usuário autenticado, executar reload/F5 em uma rota autenticada.

A arquitetura homologada mantém access token somente em memória.

Portanto, após F5, confirmar o comportamento definido no projeto:

token em memória é perdido;

sessão autenticada não é restaurada por
localStorage/sessionStorage/cookie;

novo login é exigido;

não há loop de redirect;

não há erro inesperado no console.

Não alterar essa regra para "melhorar UX" nesta fase.

11. Armazenamento

Por inspeção observável no navegador, confirmar que o JWT não foi
persistido em:

localStorage
sessionStorage
cookies de autenticação

Não registrar o conteúdo de outros dados sensíveis.

12. Se nenhum bug for encontrado

Não alterar código.

O Git diff da fase deve permanecer vazio em relação ao estado de
entrada.

13. Se um bug for encontrado

Somente então:

reproduzir;

documentar a causa;

aplicar correção mínima;

criar teste de regressão apropriado;

repetir o cenário E2E afetado;

executar a suíte frontend completa;

executar o build.

Não ampliar escopo.

Testes finais

Executar:

npm test -- --watch=false

Registrar quantidade real, failures e resultado.

Esperado:

0 failures

Build final

Executar:

npm run build

Registrar:

resultado;

initial bundle;

warnings.

Esperado:

BUILD SUCCESS

Nenhum warning relevante novo de budget.

Fora de escopo

Não implementar:

R03.2;

gráficos;

cards analíticos;

exportação CSV/PDF;

novos filtros;

novos endpoints;

npm run build aprovado.
