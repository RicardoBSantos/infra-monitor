R03.2 --- Disponibilidade por Equipamentos e Unidades --- Infra Monitor

1. Objetivo

Implementar a primeira experiência analítica real do frontend de
Relatórios, cobrindo:

Disponibilidade por Equipamentos;

Disponibilidade por Unidades;

filtros;

período;

paginação server-side;

sort server-side;

estados analíticos;

qualidade da janela;

responsividade;

acessibilidade;

integração com o backend homologado;

testes;

build.

A R03.2 deve consumir exclusivamente os endpoints já homologados na R02:

GET /api/v1/relatorios/disponibilidade/equipamentos
GET /api/v1/relatorios/disponibilidade/unidades

O Angular não deve recalcular nenhuma métrica.

2. Pré-condições

Considerar homologado:

R03.1 HOMOLOGADA

Já estão validados:

rota /relatorios;

lazy loading;

sidebar;

ADMIN, OPERADOR e VISUALIZADOR;

RelatorioApiService;

DTOs;

PageResponse;

filtros tipados;

HttpParams;

interceptor;

E2E navegador;

seis endpoints reais;

87 testes frontend;

build sem warnings.

Não reabrir essas decisões.

3. Regra fundamental

O frontend NÃO calcula:

disponibilidadePercentual
tempoMonitoradoSegundos
tempoIndisponivelSegundos
tempoDisponivelSegundos
incidentes
estadoAnalitico
qualidadeJanela
equipamentosMonitorados
equipamentosSemMonitoramento
equipamentosSemDados

Esses valores vêm prontos do backend.

Também é proibido calcular média de disponibilidade no Angular.

4. Estrutura visual

A página /relatorios deve evoluir para uma experiência funcional de
Disponibilidade.

Pode usar:

tabs;

segmented control;

subnav;

cards de seleção;

desde que coerente com o Design System existente.

Deve existir acesso claro a:

Equipamentos
Unidades

Sem criar nova rota se a arquitetura atual não exigir.

Se houver benefício real, é permitido usar subrotas:

/relatorios/disponibilidade/equipamentos
/relatorios/disponibilidade/unidades

mas apenas se isso estiver alinhado com o padrão atual do frontend.

Não criar navegação excessivamente fragmentada.

5. Filtro global de período

Implementar período obrigatório com:

inicio
fim

A UI deve usar controles de data/hora compatíveis com o restante do
sistema.

O valor enviado deve ser serializado em ISO-8601 UTC.

Não enviar string local sem conversão correta.

6. Período inicial

Não inventar período silencioso dentro do service.

A tela pode escolher um período inicial explícito de UX, desde que:

esteja visível ao usuário;

possa ser alterado;

seja enviado ao backend;

não exceda 365 dias.

Se o projeto já possui padrão de período, reutilizar.

7. Validação do período

Antes da chamada:

inicio obrigatório
fim obrigatório
inicio <= fim
máximo 365 dias

Se inválido:

não chamar backend;

mostrar erro local claro;

não esconder erro do backend caso a request chegue.

8. Filtros --- Equipamentos

Implementar filtros reais:

unidadeId
equipamentoId
monitorId
tipoEquipamentoId

Além de:

inicio
fim
page
size
sort

9. Lookups

Reutilizar endpoints existentes para selects:

GET /unidades?ativo=true
GET /tipos-equipamento?ativo=true
GET /equipamentos?unidadeId=<id>&ativo=true

Para Monitores, usar endpoint real existente e filtros adequados.

Não criar lookup fake.

10. Dependência entre filtros

Ao trocar Unidade:

limpar Equipamento incompatível;

limpar Monitor incompatível;

recarregar Equipamentos da Unidade.

Ao trocar Equipamento:

limpar Monitor incompatível;

recarregar Monitores do Equipamento.

Evitar enviar combinação hierárquica inválida ao backend quando a
própria UI já consegue impedir.

11. Disponibilidade por Equipamento --- tabela

Criar tabela responsiva com pelo menos:

Equipamento
Unidade
Monitor
Estado
Qualidade
Tempo monitorado
Tempo indisponível
Tempo disponível
Disponibilidade
Incidentes

Pode adaptar colunas no mobile.

12. Estado analítico

Representar:

CALCULADO
SEM_DADOS
SEM_MONITORAMENTO

com badge/texto coerente.

Não usar somente cor.

13. Qualidade

Representar:

PRECISA
INFERIDA

Quando null:

mostrar ausência de qualidade de forma neutra, por exemplo:

—

Não inventar PRECISA para null.

14. Disponibilidade percentual

Se valor for número:

formatar com:

2 casas decimais
%

Exemplo:

91.00%

Se null:

mostrar:

—

Não mostrar 0%.

15. Tempos

Criar helper de apresentação para segundos.

Exemplos de saída aceitável:

45s
12m 30s
2h 15m
1d 3h

O helper é apenas de formatação.

Não alterar o valor analítico.

16. Incidentes

Mostrar o número retornado pelo backend.

Se 0:

mostrar 0.

Não usar null como zero se o DTO permitir null.

17. Disponibilidade por Unidade --- tabela

Criar tabela com:

Unidade
Equipamentos total
Monitorados
Sem monitoramento
Sem dados
Tempo monitorado
Tempo indisponível
Tempo disponível
Disponibilidade
Incidentes

18. Navegação contextual

Se houver rota existente para Unidades ou Equipamentos, permitir
navegação contextual através do nome.

Exemplo:

Equipamento → /equipamentos/:id

somente se a rota existir realmente.

Não criar link quebrado.

19. Paginação Equipamentos

Server-side.

Usar:

page
size
totalElements
totalPages
first
last

Não usar paginação local.

Ao alterar filtro:

page = 0

20. Paginação Unidades

Também server-side.

Mesma regra.

21. Size

Permitir opções coerentes:

10
20
50
100

Não permitir acima de 100.

22. Sort --- Equipamentos

Expor somente whitelists homologadas pelo backend.

Campos permitidos:

equipamentoNome
unidadeNome
monitorNome
disponibilidadePercentual
tempoIndisponivelSegundos
tempoMonitoradoSegundos
incidentes

23. Sort --- Unidades

Expor somente:

unidadeNome
equipamentosTotal
equipamentosMonitorados
equipamentosSemMonitoramento
tempoIndisponivelSegundos
disponibilidadePercentual
incidentes

Não permitir campo que backend rejeita.

24. UI de sort

Pode usar:

clique no header;

select de ordenação;

combinação campo + direção.

Deve indicar claramente:

asc
desc

e o campo ativo.

25. Estado loading

Ao buscar:

mostrar loading visual;

evitar tabela vazia sem contexto;

preservar filtros visíveis.

26. Estado empty

Quando:

content=[]

mostrar mensagem contextual.

Exemplo:

Nenhum resultado encontrado para os filtros e período selecionados.

Não tratar como erro.

27. Estado error

Usar ApiError.

Diferenciar pelo menos:

400
404
401
403
500

sem criar tratamento paralelo de autenticação.

401/403 continuam no fluxo global.

28. Erro de filtro/hierarquia

Se backend retornar:

INVALID_REQUEST
RESOURCE_NOT_FOUND

mostrar mensagem de negócio de forma segura.

Não expor stack trace.

29. Refresh

Disponibilizar ação clara:

Atualizar

que refaça a consulta com os filtros atuais.

Não resetar filtros.

30. URL/query state

Se o projeto já usa query params para filtros de telas, considerar
persistir período/filtros no URL.

Se esse padrão não existir, não introduzir agora somente para
Relatórios.

31. Responsividade

Desktop:

filtros organizados;

tabela completa;

paginação visível.

Tablet:

filtros reorganizados em grid;

tabela com overflow horizontal controlado quando necessário.

Mobile:

filtros empilhados;

sem overflow da página inteira;

tabela adaptada ou scroll interno;

controles tocáveis.

Testar:

320
375
390
412
tablet
desktop

32. Acessibilidade

Garantir:

labels dos filtros;

estados loading/error/empty anunciáveis;

headers de tabela;

foco visível;

sort acessível;

botões com texto/aria-label;

badges com texto.

33. Performance frontend

Não fazer chamadas duplicadas ao mudar um único filtro.

Se usar RxJS:

evitar subscriptions vazando;

cancelar request anterior quando aplicável;

não usar polling.

Não criar cache complexo nesta fase.

34. Lookups e loading independentes

A falha de lookup não deve necessariamente derrubar a tabela inteira.

Separar:

erro de lookup
erro de relatório

quando fizer sentido.
