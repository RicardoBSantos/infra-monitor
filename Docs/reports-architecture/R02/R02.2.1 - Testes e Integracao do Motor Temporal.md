R02.2.1 --- Testes e Integração do Motor Temporal --- Infra Monitor

1. Objetivo

Homologar o motor temporal criado na R02.2 por meio de testes
determinísticos, integração com persistência PostgreSQL e validação do
ciclo temporal de Monitor/Equipamento.

Esta fase não cria novas funcionalidades de relatório.

O objetivo é provar que a matemática e a persistência do motor estão
corretas antes de qualquer avanço para R02.3.

A fase somente pode terminar como homologada se:

cenários A--P forem executados;

cenários B e C retornarem exatamente os valores esperados;

V13 for validada no PostgreSQL;

índice parcial for validado;

backfill for validado;

ciclo Monitor/Equipamento for testado;

rollback for testado;

SEM_MONITORAMENTO for integrado;

.\mvnw.cmd test executar de verdade;

.\mvnw.cmd clean package passar.

2. Fontes de verdade

Antes de alterar código, ler integralmente:

3. Regra de execução

A R02.2 terminou sem executar os testes A--P.

Isso não pode se repetir.

É proibido concluir esta tarefa com frases como:

implementado, não validado
não houve tempo para executar
compilação passou

Se um teste falhar:

executar
→ reproduzir
→ corrigir
→ executar novamente

Continuar até passar ou até existir bloqueio técnico concreto e
documentado.

4. Proibido usar skip de testes

Não usar como evidência:

-DskipTests
-Dmaven.test.skip=true

É permitido usar compilação intermediária durante desenvolvimento, mas o
aceite final exige:

.\mvnw.cmd test

com testes realmente executados.

PARTE A --- TESTES UNITÁRIOS DO CALCULADOR

5. Criar suite dedicada

Criar teste dedicado, por exemplo:

DisponibilidadeTemporalCalculatorTest

ou nomenclatura coerente.

Os cenários A--P devem existir como testes claramente identificáveis.

Preferir nomes como:

deveCalcular100PorCentoSemIncidentes
deveUnirIncidentesSobrepostos
deveIgnorarLacunaEntreJanelas
...

6. Instantes determinísticos

Não usar Instant.now() nos testes matemáticos.

Usar instantes fixos.

Exemplo:

2026-01-01T10:00:00Z

Todos os valores esperados devem ser explícitos.

7. Cenário A --- 100% disponível

Entrada:

janela: 10:00–11:00
primeira Medição: 10:00
Incidentes: nenhum

Esperado:

tempoIndisponivel = 0
tempoDisponivel = 3600
percentual = 100.00
estado = CALCULADO

8. Cenário B --- sobreposição bloqueadora

Entrada:

Incidente A: 10:10–10:30

10:10–10:40

percentual = 50.00

R02.2.1 NÃO HOMOLOGADA

9. Cenário C --- múltiplas janelas com lacuna

Entrada:

janela 2: 10:00–12:00

primeira Medição da janela 1: 08:00
primeira Medição da janela 2: 10:00

Incidente: 08:30–10:30

08:30–09:00 = 1800
10:00–10:30 = 1800

09:00–10:00

não conta.

Esperado exatamente:

tempoMonitorado = 10800
tempoIndisponivel = 3600
tempoDisponivel = 7200
percentual = 66.67

Se qualquer valor diferir:

R02.2.1 NÃO HOMOLOGADA

até correção.

PARTE B --- TESTES DA V13 NO POSTGRESQL

23. Testcontainers

Criar teste de integração PostgreSQL real/Testcontainers.

Não usar H2 para homologar:

índice parcial
migration PostgreSQL
backfill

24. Aplicação da V13

Subir schema até V12, preparar dados legados e aplicar V13 de forma
compatível com a infraestrutura de teste disponível.

Se a suíte normal sempre aplica todas as migrations automaticamente,
criar estratégia controlada para comprovar o efeito da V13.

Validar que tabela/constraints/index existem.

25. Índice parcial

Testar concretamente:

inserir janela aberta do Monitor;

tentar inserir segunda janela aberta;

banco deve rejeitar.

Depois:

fechar a primeira;

inserir nova aberta;

deve funcionar.

26. Backfill legado

Preparar:

Monitor legado
createdAt conhecido
primeira Medição conhecida
última Medição conhecida
intervaloSegundos conhecido

Validar:

inicio = max(createdAt, primeiraMedicao)
fim = ultimaMedicao + intervalo
origem = INFERIDA
fim != null

27. Legado sem Medição

Monitor sem Medição:

nenhuma janela INFERIDA criada

28. updatedAt

Adicionar asserção/teste ou inspeção SQL que prove que updatedAt não
participa do backfill.

PARTE C --- CICLO TEMPORAL PERSISTIDO

29. Testes dedicados do ciclo

Criar testes de integração para:

Monitor create active
Monitor create inactive
Monitor deactivate
Monitor reactivate
Equipment deactivate
Equipment reactivate
Monitor inactive on equipment reactivate

Usar Clock controlado.

30. Criação ativa

Com Clock fixo:

T0

Criar Monitor ativo.

Esperado:

uma janela aberta
inicio=T0
fim=null
origem=PRECISA

31. Criação inativa

Esperado:

zero janelas abertas

32. Desativação

Criar ativo em T0.

Avançar Clock para T1.

Desativar.

Esperado:

fim=T1

33. Reativação

Depois da desativação em T1, avançar para T2 e reativar.

Esperado:

janela antiga permanece fechada em T1
nova janela aberta em T2

34. Equipamento desativado

Com dois Monitores ativos e janelas abertas:

desativar Equipamento em T1

Esperado:

duas janelas encerradas em T1

35. Equipamento reativado

Com:

Monitor A ativo administrativamente
Monitor B inativo administrativamente

Reativar Equipamento em T2.

Esperado:

Monitor A → nova janela
Monitor B → nenhuma nova janela

36. Não alterar monitor.ativo

Asserção obrigatória:

reativação do Equipamento não muda monitor.ativo

37. Histórico fechado imutável

Após várias transições:

janela 1 fechada
janela 2 fechada
janela 3 aberta

A operação atual não pode alterar inicio/fim das janelas históricas
anteriores.

PARTE D --- ROLLBACK

38. Teste de rollback

Criar cenário de falha proposital dentro de transação de alteração
administrativa + janela.

Objetivo:

nenhuma metade da operação persiste

Exemplo:

status do Monitor alterado
falha antes/depois da janela

Após rollback:

status original preservado
janela original preservada

Não simular apenas em unit test sem transação real.

PARTE E --- INTEGRAÇÃO SEM_MONITORAMENTO

39. Integrar camada de preparação

Criar ou completar a camada que produz resultado analítico para
Equipamentos filtrados.

Ela deve:

localizar Equipamento;

localizar Monitores ICMP;

se nenhum existir, produzir SEM_MONITORAMENTO;

se existirem, produzir um resultado independente por Monitor.

Não consolidar Monitores.

40. Tipagem

Usar tipos explícitos.

Não usar:

Map<String,Object>

como resultado final dessa camada.

Pode reutilizar ResultadoDisponibilidadeTemporal ou criar
projection/DTO interno adequado.
