PARTE A --- DISPONIBILIDADE POR EQUIPAMENTO

5. Problema atual

A disponibilidade por Equipamento ainda é paginada em memória após o
motor temporal.

Isso não atende o contrato.

A solução deve preservar a correção global da ordenação e paginação.

6. Paginação server-side --- campos não calculados

Para sort baseado em campos de cadastro:

equipamentoNome
unidadeNome
monitorNome

é permitido usar estratégia:

SQL filtra candidatos
→ COUNT real
→ ORDER BY server-side
→ LIMIT/OFFSET
→ retorna apenas candidatos da página
→ motor temporal calcula apenas a página

Desde que:

totalElements represente o conjunto filtrado completo;

ordem seja global;

nenhum candidato da página seja perdido;

SEM_MONITORAMENTO continue aparecendo conforme contrato.

7. Sort por métricas calculadas

Para:

disponibilidadePercentual
tempoIndisponivelSegundos
tempoMonitoradoSegundos
incidentes

é PROIBIDO:

paginar candidatos
→ calcular página
→ ordenar apenas a página

Isso produz ordenação global incorreta.

Nesses campos, implemente estratégia server-side que calcule ou projete
a métrica antes de aplicar:

ORDER BY
LIMIT
OFFSET

Pode usar:

native SQL;

CTE;

projection;

query temporal equivalente;

materialização temporária apenas dentro da query;

abordagem PostgreSQL coerente.

Não carregar o conjunto completo em Java só para ordenar.

8. Count da Disponibilidade por Equipamento

Implementar COUNT real do universo analítico filtrado.

O count deve respeitar:

unidadeId
equipamentoId
monitorId
tipoEquipamentoId

e a regra de uma linha por Monitor ICMP, incluindo a semântica de
SEM_MONITORAMENTO prevista pelo contrato.

Documentar claramente o que uma "linha" representa no count.

PARTE B --- DISPONIBILIDADE POR UNIDADE

9. Paginação server-side

A lista de Unidades deve ser:

filtrada no banco
ordenada no banco
paginada no banco
count no banco

Depois, o serviço pode calcular as métricas apenas para as Unidades da
página, desde que o sort não dependa de métricas calculadas.

10. Sort por métricas de Unidade

Para:

equipamentosTotal
equipamentosMonitorados
equipamentosSemMonitoramento
tempoIndisponivelSegundos
disponibilidadePercentual
incidentes

a ordenação precisa ser global antes da paginação.

Não ordenar somente as Unidades já paginadas.

Usar query agregada/server-side apropriada.

PARTE C --- LATÊNCIA

11. Sort server-side

Implementar ordenação server-side para:

unidadeNome
equipamentoNome
monitorNome
minLatenciaMs

count

Sem carregar tudo para Java.

12. Segurança do sort

Usar whitelist/mapeamento:

campo público
→ expressão SQL conhecida

Nunca concatenar diretamente o parâmetro do cliente.

PARTE D --- NOTIFICAÇÕES

13. Sort server-side

Implementar:

createdAt
enviadoEm
status
canal
tipoEvento
tentativas

no banco.

Campos nullable devem ter comportamento determinístico.

14. Null ordering

Definir e documentar para:

enviadoEm
encerradoEm
latenciaMs

por exemplo:

ASC → NULLS LAST
DESC → NULLS LAST

ou política equivalente consistente.

Não deixar comportamento implícito e diferente entre endpoints.

PARTE F --- SORT

16. Asc/desc

Testar em cada família de endpoint pelo menos:

sort=campo,asc
sort=campo,desc

17. Campo inválido

Exemplo:

sort=senhaHash,asc

Esperado:

400 INVALID_REQUEST

18. Direção inválida

Exemplo:

sort=nome,sideways

Esperado:

400 INVALID_REQUEST

19. Injection

Testar entrada segura equivalente a:

sort=nome desc; drop table usuarios,asc

Esperado:

400 INVALID_REQUEST

Nenhuma parte arbitrária pode chegar ao ORDER BY.
