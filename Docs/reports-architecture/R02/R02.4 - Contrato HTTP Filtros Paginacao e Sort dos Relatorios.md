R02.4 --- Contrato HTTP, Filtros, Paginação e Sort dos Relatórios --- Infra Monitor

1. Objetivo

Concluir o contrato HTTP do backend de Relatórios sobre as regras de
negócio já homologadas nas fases anteriores.

A R02.4 deve fechar exclusivamente:

validação obrigatória de período;

limites por endpoint;

filtros REST;

coerência hierárquica dos filtros;

IDs inexistentes;

paginação server-side com count real;

size máximo;

whitelist de sort;

direção de ordenação;

mapeamento seguro de sort para SQL;

DTOs públicos nos controllers;

códigos de erro;

RBAC HTTP real;

smoke tests HTTP dos seis endpoints;

documentação final do contrato backend de Relatórios;

regressão e build.

A R02.4 não deve alterar as fórmulas temporais, agregação por
Unidade, p95 ou DTOs analíticos já homologados, salvo bug concreto
reproduzido.

4. Parâmetros comuns

Todos os endpoints devem receber:

inicio
fim

como Instant ISO-8601 UTC.

Eles são obrigatórios.

Ausência de qualquer um:

400 INVALID_REQUEST

ou código equivalente já homologado pelo projeto para request inválida.

Preservar padrão global ApiError.

5. Limites de período

Aplicar:

Endpoint                           Limite

disponibilidade/equipamentos     365 dias
disponibilidade/unidades         365 dias
incidentes                       365 dias
medicoes                          31 dias
latencia                          90 dias
notificacoes                     365 dias

Regras:

inicio > fim
→ 400 INVALID_REQUEST

período acima do limite
→ 400 INVALID_REQUEST

inicio = fim
→ permitido

Não duplicar validação entre controllers.

Criar serviço/helper central para período se já não existir.

12. IDs inexistentes

Para qualquer filtro de ID explicitamente informado:

unidadeId
tipoEquipamentoId
equipamentoId
monitorId
incidenteId

se o recurso não existir:

404 RESOURCE_NOT_FOUND

Não retornar simplesmente content=[].

Isso evita ambiguidade entre:

recurso inexistente

e:

recurso válido sem dados no período

13. Validação hierárquica

Se IDs existirem, validar relações.

Exemplos obrigatórios:

equipamentoId não pertence à unidadeId
→ 400 INVALID_REQUEST

monitorId não pertence ao equipamentoId
→ 400 INVALID_REQUEST

monitorId não pertence à unidadeId
→ 400 INVALID_REQUEST

equipamentoId não pertence ao tipoEquipamentoId
→ 400 INVALID_REQUEST

Se tipoEquipamentoId e unidadeId forem usados sem equipamentoId,
filtrar normalmente.

Não tratar combinação incoerente como lista vazia.

14. incidenteId em Notificações

Se incidenteId informado não existir:

404 RESOURCE_NOT_FOUND

Se existir e não houver Notificações no período:

200
content=[]

15. Paginação padrão

Todos os seis endpoints retornam:

{
"content": [],
"page": 0,
"size": 20,
"totalElements": 0,
"totalPages": 0,
"first": true,
"last": true
}

Reutilizar PaginaResposta<T> já existente.

Não criar segundo envelope.

16. Defaults

Defaults:

page=0
size=20

Para Medições:

page=0
size=50

Máximo global:

size=100

Se o padrão atual do backend limita valores acima de 100 para 100:

preservar esse comportamento.

Não alterar silenciosamente para erro se o restante da API usa clamp.

17. page inválido

Validar conforme convenção já existente no backend.

Se page < 0:

400 INVALID_PARAMETER

ou código global equivalente.

18. size inválido

Se:

size <= 0

retornar erro coerente com API atual.

Se:

size > 100

aplicar máximo 100 se esse é o contrato atual.

19. Count real

A paginação precisa utilizar total real do conjunto filtrado.

Não usar:

content.size()

como totalElements.

Para queries JDBC/nativas, implementar query de count equivalente aos
filtros do endpoint.

Critério:

totalElements
totalPages
first
last

devem permanecer corretos em todas as páginas.

21. Sort --- formato

Aceitar padrão atual:

sort=campo,asc
sort=campo,desc

Direções públicas:

asc
desc

Case sensitivity deve seguir convenção existente.

Direção inválida:

400 INVALID_REQUEST

22. Segurança do sort

Nunca concatenar diretamente valor arbitrário fornecido pelo cliente.

Implementar mapa explícito:

nomeCampoPublico
→ expressão SQL conhecida

Somente a expressão mapeada entra na query.

Evitar SQL injection via sort.

29. Sort inválido

Campo não permitido:

400 INVALID_REQUEST

Não ignorar silenciosamente.

Exemplo:

sort=senhaHash,asc

deve retornar erro.

30. Sort default

Definir default por endpoint com base no comportamento
atual/documentação.

Se a R01/R02 não fixou default específico, preservar a ordenação já
implementada no relatório e documentar.

Não escolher defaults contraditórios entre query e documentação.

31. Sort e null

Ordenação de campos nullable deve ser determinística.

Exemplo:

encerradoEm
enviadoEm
latenciaMs

Definir comportamento coerente PostgreSQL.

Se usar NULLS FIRST/LAST, documentar.

Não é necessário expor parâmetro público para null ordering.

32. DTOs no Controller

Controllers devem retornar:

PaginaResposta<DisponibilidadeEquipamentoResponse>
PaginaResposta<DisponibilidadeUnidadeResponse>
PaginaResposta<HistoricoIncidenteResponse>
PaginaResposta<HistoricoMedicaoResponse>
PaginaResposta<LatenciaIcmpResponse>
PaginaResposta<HistoricoNotificacaoResponse>

Não retornar:

PaginaResposta<Map<String,Object>>

33. Erros

Preservar ErroResposta/ApiError.

Casos esperados:

VALIDATION_ERROR
INVALID_ENUM
INVALID_PARAMETER
INVALID_REQUEST
RESOURCE_NOT_FOUND
UNAUTHORIZED
FORBIDDEN

Não introduzir formato de erro exclusivo para Relatórios.

34. RBAC

Todos os seis endpoints exigem JWT.

Leitura permitida para:

ADMIN
OPERADOR
VISUALIZADOR

Sem token:

401 UNAUTHORIZED

Usuário autenticado com papel válido:

200

Não criar permissão especial de Relatórios nesta fase.

35. PASSWORD_CHANGE_REQUIRED

Usuário com:

trocaSenhaObrigatoria=true

não pode usar os endpoints de Relatórios enquanto não trocar a senha,
conforme regra global já homologada.

Teste ao menos um endpoint:

403 PASSWORD_CHANGE_REQUIRED

36. Conta inativa

JWT emitido antes da desativação:

GET /api/v1/relatorios/...
→ 401 UNAUTHORIZED

se essa já é a regra global.

Não alterar comportamento de Auth.

37. CORS

Nenhuma alteração conceitual.

Confirmar que endpoints aceitam:

Authorization

pela configuração global.

Não adicionar @CrossOrigin.
