R02.3.1 --- Correção dos Mapeamentos JDBC e Homologação da R02.3 --- Infra Monitor

1. Objetivo

Concluir e homologar a R02.3 corrigindo exclusivamente os bugs concretos
identificados nos testes PostgreSQL:

leitura de TIMESTAMPTZ para Instant;

mapeamento do retorno de percentile_cont(0.95) para o valor final
de p95 em milissegundos.

Esta fase não deve criar funcionalidades novas.

Ao final, a R02.3 somente pode ser considerada homologada se:

os 6 testes de RelatoriosAnaliticosPostgresIntegrationTest
passarem;

o cenário U2 produzir exatamente 91.00;

o p95 produzir exatamente 96 para o dataset definido;

Incidentes analíticos passarem;

Medições analíticas passarem;

Notificações analíticas passarem;

a suíte backend completa passar;

clean package passar.

2. Estado recebido da R02.3

A R02.3 terminou bloqueada por dois bugs de mapeamento JDBC.

Bug 1 --- TIMESTAMPTZ

O driver PostgreSQL não converteu diretamente:

ResultSet#getObject(..., Instant.class)

no contexto das queries analíticas.

Esse problema afeta pelo menos:

Incidentes;

Medições;

Notificações;

qualquer outro mapper que leia TIMESTAMPTZ da mesma forma.

Bug 2 --- p95

percentile_cont(0.95) retorna valor numérico compatível com
Double/Number.

O mapper atual tenta converter/castar diretamente para Integer,
causando erro.

3. Escopo estrito

Implementar somente:

correção segura de TIMESTAMPTZ → Instant;

correção segura de p95 Number → inteiro HALF_UP;

testes de regressão dos mapeamentos;

regressão backend completa;

build final;

atualização mínima de documentação, se necessária.

PARTE A --- TIMESTAMPTZ → INSTANT

5. Estratégia recomendada

Centralizar a leitura temporal JDBC.

Preferir uma função/helper reutilizável equivalente a:

private Instant getInstant(ResultSet rs, String column) throws SQLException {
OffsetDateTime value = rs.getObject(column, OffsetDateTime.class);
return value == null ? null : value.toInstant();
}

ou solução equivalente segura e compatível com o driver PostgreSQL
atual.

O contrato público continua usando:

Instant
ISO-8601 UTC

6. Null safety

Campos temporais nullable devem continuar funcionando.

Exemplos:

encerradoEm = null
enviadoEm = null

Esperado:

null

e não exceção.

7. Centralização

Evitar duplicar conversões diferentes em:

mapper de Incidente;

mapper de Medição;

mapper de Notificação;

mapper de Disponibilidade;

demais queries JDBC.

Criar helper interno/coerente, sem introduzir abstração excessiva.

8. Não alterar timezone de negócio

O uso de OffsetDateTime é apenas ponte JDBC.

No domínio/API final:

Instant
UTC

Não mudar DTOs públicos para OffsetDateTime apenas para contornar o
driver.

PARTE B --- P95

9. Origem

A query permanece:

percentile_cont(0.95)
WITHIN GROUP (ORDER BY latencia_ms)

Não remover percentile_cont.

Não calcular percentil em Java.

10. Conversão segura

Tratar o valor retornado como:

Number
Double
BigDecimal

ou equivalente, sem cast direto para Integer.

Fluxo conceitual:

valor SQL = 95.5
→ representação decimal
→ HALF_UP
→ 96

11. Null

Se não houver sucessos:

p95 = null

Não tentar arredondar null.

12. Regra final

p95LatenciaMs continua:

Integer

ou tipo inteiro definido no contrato atual.

Arredondamento:

HALF_UP
