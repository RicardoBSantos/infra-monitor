R04.1 — Arquitetura e Contratos de Exportação de Relatórios — Infra Monitor

1. Objetivo

Definir a arquitetura, contratos HTTP, regras de segurança, limites operacionais e comportamento de UX para exportação dos Relatórios do Infra Monitor.

Esta fase é exclusivamente de arquitetura e contrato.

NÃO implementar exportação CSV ou PDF nesta fase.

O objetivo é produzir uma especificação sólida para as fases seguintes:

R04.2 — Backend CSV
R04.3 — Frontend CSV
R04.4 — PDF
R04.5 — Homologação integrada / segurança / performance
R04.6 — Fechamento

2. Estado homologado de entrada

Considerar homologados:

R02 — Backend de Relatórios
R03 — Frontend de Relatórios

Relatórios existentes:

Disponibilidade por Equipamentos
Disponibilidade por Unidades
Incidentes
Medições
Latência ICMP
Notificações
Visão Geral

A R04 deve reutilizar as regras analíticas já existentes.

Não duplicar lógica de cálculo.

3. Regra arquitetural principal

A exportação deve ser produzida pelo BACKEND.

É proibido:

Angular buscar page 0
Angular buscar page 1
Angular buscar page 2
...
Angular concatenar registros
Angular gerar CSV

A exportação deve partir diretamente da mesma semântica analítica usada pelos endpoints homologados.

Objetivo:

tela e arquivo precisam representar o mesmo contrato analítico

4. Escopo inicial

Definir exportação para:

Disponibilidade por Equipamentos
Disponibilidade por Unidades
Incidentes
Medições
Latência
Notificações

A Visão Geral deve ser analisada separadamente.

Por padrão:

Visão Geral NÃO será exportada como CSV na primeira versão

Motivo:

é uma composição de diferentes fontes e agregações, não um dataset tabular único.

Registrar decisão final.

6. Estratégia: síncrona ou assíncrona

Avaliar explicitamente:

exportação síncrona
exportação assíncrona

Critérios:

volume atual;

limites máximos de período;

número esperado de registros;

memória;

tempo de resposta;

UX;

infraestrutura disponível;

necessidade de job/background;

storage temporário;

complexidade operacional.

Para o MVP, preferir solução síncrona se os limites permitirem.

Não introduzir fila/job/storage sem necessidade comprovada.

Registrar decisão e justificativa.

7. Formato CSV

Definir:

encoding: UTF-8
separator: ,
line ending: padrão consistente
header: obrigatório
quote/escaping: RFC 4180 ou estratégia equivalente

Avaliar inclusão de BOM UTF-8 somente se necessário por compatibilidade com Excel no ambiente alvo.

Registrar decisão.

8. Content-Type

Definir contrato HTTP, preferencialmente:

text/csv; charset=UTF-8

Confirmar estratégia final.

9. Content-Disposition

Definir:

attachment

com filename seguro.

Exemplo conceitual:

disponibilidade-equipamentos_2026-08-01_2026-08-25.csv

Não colocar:

e-mail do usuário;

nome pessoal;

JWT;

ID sensível;

parâmetros brutos perigosos.

10. Nome dos arquivos

Definir padrão determinístico.

Sugestão:

<relatorio>_<inicio>_<fim>.csv

Exemplos:

disponibilidade-equipamentos_2026-08-01_2026-08-25.csv
disponibilidade-unidades_2026-08-01_2026-08-25.csv
incidentes_2026-08-01_2026-08-25.csv
medicoes_2026-08-01_2026-08-25.csv
latencia_2026-08-01_2026-08-25.csv
notificacoes_2026-08-01_2026-08-25.csv

Sanitizar qualquer componente variável.

11. Filtros

A exportação deve reutilizar exatamente os filtros homologados dos relatórios.

Não criar filtro novo exclusivo da exportação sem justificativa.

Disponibilidade Equipamentos

Auditar e preservar filtros reais, como:

inicio
fim
unidadeId
equipamentoId
monitorId
tipoEquipamentoId

Disponibilidade Unidades

Auditar filtros reais.

Incidentes

Auditar:

inicio
fim
unidadeId
equipamentoId
monitorId
status

e demais filtros realmente existentes.

Medições

Auditar filtros reais.

Latência

Auditar filtros reais.

Notificações

Auditar:

inicio
fim
incidenteId
status
canal
tipoEvento

Somente o contrato real deve ser documentado.

12. Sort

Decidir se exportação:

A. respeita sort solicitado pelo usuário
ou
B. usa ordem fixa documentada

Preferência:

respeitar o sort homologado do relatório

quando suportado.

Sort inválido deve seguir a mesma validação atual.

Não aceitar SQL/arbitrary sort.

13. Paginação

Exportação NÃO deve aplicar paginação visual da tela.

A exportação representa:

todo o conjunto resultante dos filtros

dentro do limite operacional.

Não exportar somente a página atual, salvo se isso for uma opção explicitamente definida e nomeada, o que não faz parte do V1 por padrão.

14. Limites operacionais

Definir limites de exportação.

Critérios possíveis:

máximo de linhas
máximo de período
timeout
máximo de bytes

Reutilizar limites temporais homologados:

Disponibilidade: 365 dias
Incidentes: 365 dias
Medições: 31 dias
Latência: 90 dias
Notificações: 365 dias

Avaliar limite adicional de linhas.

Exemplo conceitual:

50.000 linhas
100.000 linhas

NÃO fixar valor sem analisar volume e performance.

Registrar decisão final.

15. Comportamento ao exceder limite

Definir erro de negócio claro.

Exemplo conceitual:

EXPORT_LIMIT_EXCEEDED

Avaliar integração com o padrão de ApiError/ErroResposta.

Não devolver 500 para limite operacional previsível.

Preferência:

400 ou 422

conforme contrato existente e convenções do projeto.

Registrar decisão.

16. Segurança — CSV Injection

Obrigatório tratar CSV Injection / Formula Injection.

Valores iniciados com caracteres perigosos como:

=
+
-
@

devem ser tratados quando provenientes de texto livre ou dados potencialmente controlados por usuário.

Definir estratégia segura, por exemplo:

prefixar com '

ou abordagem equivalente documentada.

Não alterar semanticamente campos numéricos reais.

17. Escaping CSV

Definir tratamento para:

vírgula
aspas
quebra de linha
carriage return

Campos contendo caracteres especiais devem ser corretamente escapados.

Testes futuros serão obrigatórios.

18. Campos proibidos

Nenhuma exportação pode conter:

senha
senhaHash
JWT
Authorization
JWT_SECRET
BOOTSTRAP_ADMIN_PASSWORD
Telegram bot token
Telegram chat secret
stack trace
internal exception
entity internals
audit internals não previstos

Exportação deve partir de DTO explícito.

Nunca serializar entidade JPA genérica.

19. RBAC

Exportação deve seguir o mesmo READ dos Relatórios:

ADMIN
OPERADOR
VISUALIZADOR

Todos podem exportar os relatórios que já podem visualizar.

Não criar permissão separada no V1 salvo necessidade real.

Sem JWT:

401

Usuário inativo:

seguir comportamento atual.

PASSWORD_CHANGE_REQUIRED:

preservar bloqueio atual.

20. CORS

Download via Angular continuará usando Bearer.

Auditar se CORS precisa expor:

Content-Disposition

para o frontend ler filename.

Se necessário, definir:

Access-Control-Expose-Headers: Content-Disposition

sem alterar credentials=false.

Registrar decisão.

21. Endpoints propostos

Definir contratos finais.

Uma opção preferencial:

GET /api/v1/relatorios/disponibilidade/equipamentos/export
GET /api/v1/relatorios/disponibilidade/unidades/export
GET /api/v1/relatorios/incidentes/export
GET /api/v1/relatorios/medicoes/export
GET /api/v1/relatorios/latencia/export
GET /api/v1/relatorios/notificacoes/export

Avaliar se:

/export?format=csv

é necessário.

Para V1, se apenas CSV existir:

/export

pode ser suficiente.

Não implementar ainda.

22. Método HTTP

Avaliar:

GET
POST

Como filtros já são query params e não há side effect, GET é candidato natural.

Porém avaliar:

comprimento da URL;

número de filtros;

cache;

semântica HTTP.

Registrar decisão.

29. Representação de null

Definir padrão.

Preferência para CSV:

campo vazio

Não escrever:

null
undefined
NaN
—

O símbolo — pertence à apresentação visual, não necessariamente ao formato de dados exportado.

Registrar decisão final.

30. Datas

API trabalha em ISO-8601 UTC.

Definir CSV preferencialmente com datas em:

ISO-8601 UTC

Exemplo:

2026-08-25T14:32:10Z

Não exportar data local ambígua.

31. Decimais

Definir formato independente de locale.

Preferência:

ponto decimal

Exemplo:

91.00
55.25

Não misturar vírgula decimal com separador CSV vírgula sem estratégia de escaping clara.

32. Enums

Exportar enums como strings estáveis do contrato:

Somente valores reais.

Não traduzir enum no arquivo V1, salvo decisão explícita.

34. Streaming

Avaliar geração:

em memória
streaming HTTP

Preferir streaming se o volume justificar.

Não carregar centenas de milhares de registros em uma List sem análise.

Registrar estratégia recomendada para R04.2.

35. Banco e queries

Exportação deve evitar:

N+1
OFFSET profundo página por página
loop frontend/backend
carregar entidades completas

Preferir query dedicada/streaming ou reutilização segura dos repositórios analíticos.

36. Timeout

Definir expectativa operacional.

Não permitir request ilimitada.

Avaliar timeout de aplicação/proxy se houver.

Registrar risco para deploy.

37. Auditoria

38. Filename no frontend

fallback determinístico.

Não usar nome enviado pelo usuário sem sanitização.

40. Erros futuros

Definir comportamento para:

400 INVALID_REQUEST
404 RESOURCE_NOT_FOUND
403 FORBIDDEN
401 UNAUTHORIZED
EXPORT_LIMIT_EXCEEDED
500 INTERNAL_ERROR

Erro HTTP deve continuar sendo JSON ApiError/ErroResposta.

41. PDF — arquitetura futura

Avaliar:

Registrar candidatos/riscos.

Registrar:

CSV = datasets tabulares
PDF = apresentação consolidada

como hipótese arquitetural, se aprovada.
